02 · W5 → W6

在互動流程中加入網路

使用者操作按下載入
→
JavaScript呼叫 fetch()
→
HTTPRequest / Response
→
資料與畫面JSON → DOM
async function loadData() {
  const response = await fetch("json/dashboard_cards.json");

  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }

  const data = await response.json();
  renderCards(data.dashboard);
}
  • fetch(url)：送出請求並回傳一個 Promise。
  • await：等候非同步結果，不會因此凍結整個瀏覽器畫面。
  • response.ok：HTTP status 是否為成功範圍；404/500 不會自動讓 fetch reject。
  • response.json()：解析 response body，解析失敗也需要處理。

03 · AJAX & HTTP

AJAX 是一種互動方式，不是程式語言

AJAX 是 JavaScript 在背景向 Server/API 傳送或取得資料的做法。現代網站通常傳 JSON； 收到資料後只更新需要的 DOM，不必重整整頁。

狀態常見意思先檢查什麼
200 OK請求成功Response body 格式及畫面 render。
400 Bad Request請求格式或參數不正確URL、method、query、request body。
401 Unauthorized尚未登入或認證資料無效登入狀態、token 與後端認證流程。
403 Forbidden身分或權限不足帳號權限、OAuth scope 或 API 設定。
404 Not Found資源或路徑不存在API URL、路由、資源 ID。
500伺服器發生錯誤後端 log 與 API response。
兩種不同的失敗

HTTP 404 是有收到伺服器回應但狀態不成功；Network error 則可能是連線、DNS 或瀏覽器安全政策問題。都要明確呈現錯誤，不要把錯誤假裝成空資料。

05 · API KEY & OAUTH

認證方式不同，不能混為一談

公開 API

不需要登入即可讀取；仍要遵守服務的使用條款與流量限制。

API Key

通常識別應用程式或專案。放在瀏覽器的 Key 可被使用者看到；依服務支援設定來源、API 與額度限制，不要假設它是秘密。

OAuth Access Token

代表使用者授權的範圍，應依 OAuth 流程取得並妥善處理；Access Token 與 API Key 是不同用途。

使用者 → Google 登入 / 同意授權 → OAuth
       → Access Token → fetch() → Google API → JSON
絕不可把真正的 Secret 放入前端

Client Secret、Service Account private key、Refresh Token、資料庫密碼等不能寫進 HTML/JavaScript 或上傳公開 repo。需要保密的認證與 token 交換應由後端完成。

本 repo 頁面不實作 Google 登入或 API 呼叫。若後續由 FastAPI 提供登入端點，前端應呼叫同一網站的後端 session API；後端負責驗證 Google 身分及 session cookie。

06 · CORS

CORS 是瀏覽器執行的跨來源讀取規則

Origin 由 scheme、host、port 組成。像 http://localhost:5500 與 http://localhost:8000 是不同 origin，因為 port 不同。 跨來源時，瀏覽器會依 API 回應中的 CORS headers 判斷網頁 JavaScript 是否可以讀取 response。 

Frontend: http://localhost:5500
API:      http://localhost:8000

API response 可能包含：
Access-Control-Allow-Origin: http://localhost:5500
curl / Postman 成功，瀏覽器卻顯示 CORS error，並不矛盾

curl 和 Postman 不會替網頁執行 Same-Origin Policy。瀏覽器才會限制 JavaScript 讀取未獲允許的跨來源 response。CORS 通常要由 API 伺服器或平台設定；在前端自行加上 response header 並不能授權伺服器。

Preflight：真正請求前的詢問

部分跨來源請求會先送 OPTIONS 詢問伺服器是否允許指定的 method/header；不是每個 fetch 都會 preflight。

Browser ── OPTIONS preflight ──→ API
Browser ←─ CORS policy headers ─ API
Browser ── actual request ──────→ API (如果 preflight 通過)

07 · DEBUGGING

依照請求到畫面的順序找問題

  1. Request：URL、HTTP method、query/body 是否正確？
  2. Network：請求有沒有送出？HTTP status 和 response body 是什麼？有沒有 OPTIONS？
  3. Authentication：是否需要 API Key、OAuth access token 或正確 scope？
  4. CORS：Frontend/API origin 是否不同？response 是否有允許目前 origin 的 headers？
  5. JSON：body 能否解析？資料欄位是否符合預期？
  6. DOM：render function 是否執行？是否使用安全的 DOM API 更新畫面？
我的 Browser fetch() 發生錯誤。請不要先重寫程式。
1. 先確認 Frontend origin 與 API origin。
2. 檢查 Network 的 URL、method、status、response body。
3. 判斷是否有 OPTIONS preflight 和 CORS response headers。
4. 分辨 HTTP、Network、OAuth/token、JSON 或 DOM 問題。
5. 指出應修改 Frontend、Backend、OAuth 或 API Console 的哪一層，
   再提出最小修正方式。

08 · GOOGLE CLOUD CHECKLIST

串接 Google API 前逐項確認

  1. 建立或選擇正確的 Google Cloud Project。
  2. 確認目標 API 已啟用。
  3. 設定正確類型的 OAuth Client。
  4. 確認 Authorized JavaScript Origins 與 Redirect URI 完全符合實際網址。
  5. 只要求必要的 OAuth scopes。
  6. 確認 Token 由正確流程取得、傳給正確 API，且不把 Client Secret 或 Refresh Token 放進前端。

Client ID、Redirect URI、已啟用的 API、Scopes 與允許來源都要依實際專案確認，不要讓 AI 猜測或自行補上。

09 · AI CODING REVIEW

AI 串接 API 後，自己要能回答

  1. fetch() 在哪個 function？什麼 Event 會觸發它？
  2. Request 的 URL、HTTP method 與認證方式是什麼？
  3. 成功時 response 是什麼格式？哪個 function 解析 JSON 並更新 DOM？
  4. HTTP 非成功狀態、Network error、JSON 錯誤和空資料如何處理？
  5. 是否跨 origin？若有 CORS 問題，應檢查哪個 server response / 設定？
  6. 有沒有把 Client Secret、Refresh Token 或其他敏感資料放進前端？
W6 核心流程

Event → Function → fetch() → HTTP/API → JSON → Function → DOM → UI

完成本週實作後，記錄一個 HTTP、OAuth/token、CORS、JSON 或 DOM 問題，以及你如何定位它。
